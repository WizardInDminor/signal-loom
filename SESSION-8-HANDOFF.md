## 4. Safety, data and interoperability review

- **Does any normal action transmit MIDI?** **No.** The bridge has no path to the Live service; loading, editing, reviewing and downloading produce zero MIDI.
- **Hardware writes/configuration changes possible?** **No.** The only output is a downloaded JSON file; applying it is a manual step in the official editor, which the UI tells the user not to do without the untouched baseline and the owner procedure (S9-E01/E02).
- **Data preservation, exports, restore and backward compatibility:** rig documents, profiles, images, manuals, Scenes and Textures are untouched. Every operation carries whole preset objects (routing, mode, bypass, spillover, unknown keys) verbatim; untouched presets, bank wrappers, controller settings and unknown keys at every level are compared object-for-object after the transaction and a failed check refuses the proposal; a no-op returns the input byte for byte; `byte_identical_to_input` and `structurally_identical_to_input` are reported separately.
- **Unverifiable inputs:** a missing / mismatched hash, a foreign schema version or dump type, or a structural deviation from the real backup blocks any proposal (refused with reasons, no file); inspection continues.
- **Unknown or unsupported protocol/file fields:** preserved verbatim and listed; editing them is refused; `matrixArray`, `bypass`, `tipT`, `ringT`, global settings and trails are read-only.
- **Manufacturer-documented vs user-declared vs owner-observed claims:** every evidence note in the response (`evidence` block) and the docs is tagged; nothing in this sprint is owner-observed hardware evidence.
- **Potential irreversible actions, hazards or sound-level risks:** none inside Signal Loom. Restoring a `full` backup in the official editor may replace all 512 presets and the controller settings — stated in the UI, the API warnings and the owner package.
- **Safe rollback/revert path and backup required:** revert the PR (no migrations, no data changes). For the owner's ML10X: the untouched Device Backup exported before any restore.

- **Working backup/restore steps, baseline snapshots and safe audio precautions:**
  1. In the editor, export a **Device Backup**. Keep it untouched as the recovery baseline (private; never commit). Export a second copy and compare the two in the Bridge (*Routing experiment*) to confirm exports are repeatable (expect 0 preset changes; the hash and date may differ).
  2. Amp muted for anything beyond S9-E01; nothing in S9-E01 makes sound.
- **Test steps:**
  1. **S9-E01 (editor only, no restore).** Load the baseline in Signal Loom → *Manage presets* → rename one **disposable** preset (append " SL", ≤12 characters) → *Review* (expect "1 value change", self-check OK, all preservation checks OK) → download. In the editor, *Controller Backup → Restore / Choose File* with the candidate **only as far as the editor parses the file** — record whether it accepts the file (name shown, no error) or rejects it (exact message). **Do not confirm a restore.** If the editor's parse step cannot be separated from the device write, stop here and record that; S9-E02 covers the write under its own gate.
  2. **S9-E03 (editor only).** Repeat step 1 with a 13-character name (tick *Keep as typed*). Record what the editor shows for that preset name after parsing.
  3. **S9-E02 (separately authorized full-device restore).** Prerequisites: S8-E01's characterization of what Restore sends; the baseline from above; a recovery plan independently checked (restore the baseline in the editor and confirm the device recalls a known preset correctly); amp muted; Persist state recorded. Restore the candidate from step 1. Re-export a Device Backup. In Signal Loom, compare it with the baseline (*Routing experiment* + the structural diff): expect exactly the renamed preset to differ by `presetName` only, every other preset and every controller field identical. On the device, recall a known preset and check its LEDs / audio path against before. Then restore the baseline and re-export again to prove recovery.
- **Expected observable outcomes:** S9-E01: the editor lists / accepts the candidate without an error. S9-E02: the re-export differs from the baseline in the one proposed slot only; the device behaves as before on a known preset; the baseline restore brings the re-export back to identical presets.
- **Pass/fail criteria, what to do on partial/failure, stop/disarm and restoration:** PASS = accepted / only the proposed slot differs. PARTIAL = accepted but other fields differ (record which; keep both files; stop). FAIL = the editor refuses the file (record the message; nothing was written) or the device state differs unexpectedly after restore → restore the baseline immediately, re-export, compare, record. If Persist changed state after a restore (a known 1.2 beta anomaly), record it and set it back from the device menu.
- **What this test does not prove:** that copy / move / swap candidates behave on the device (repeat S9-E02 per operation class only after the rename passes); anything about routing authorship; that future editor builds accept the same file; CC / SysEx behaviour.
